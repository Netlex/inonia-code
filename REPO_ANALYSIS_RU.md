# Анализ репозитория `inonia-code` (Kilo Code)

## 1) Что это за проект

Этот репозиторий — монорепозиторий AI-инструмента **Kilo Code**: основной продукт — расширение для VS Code, дополнительно есть CLI, webview-интерфейс, пакеты общих типов/облака/телеметрии, e2e/оценки, а также реализация для JetBrains.

## 2) Архитектура верхнего уровня

- **Основное расширение VS Code**: `src/`.
- **UI webview**: `webview-ui/` (React + Vite).
- **CLI**: `cli/` (TUI/автономный режим).
- **Общие пакеты**: `packages/*`:
    - `types`, `cloud`, `telemetry`, `ipc`, `evals`, build/config-пакеты.
- **Интеграция с JetBrains**: `jetbrains/` (host на TS + плагин на Kotlin).
- **Тестовые/вспомогательные приложения**: `apps/*` (storybook, e2e, docs и др.).

## 3) Технологический стек

- Ядро монорепо: **pnpm workspaces + Turborepo**.
- Основной язык: **TypeScript** (очень большой объём кода), UI — **React/TSX**.
- Расширение VS Code использует webview, много интеграций с LLM/API, терминалом, файловой системой, MCP, индексом кода.
- Есть кросс-IDE направление через JetBrains-плагин.

## 4) Что видно по структуре и масштабам

- По объёму (без `node_modules` и `.git`) крупнейшие зоны:
    - `src/` — ядро extension.
    - `webview-ui/` — интерфейс.
    - `cli/` — терминальный интерфейс.
    - `apps/`, `jetbrains/`, `packages/` — вспомогательная и платформенная инфраструктура.
- Большое количество тестов в нескольких подпроектах (`vitest`, e2e, тесты автодополнения и т.д.).
- Видно зрелый продуктовый pipeline: lint, type-check, test, bundle/vsix, nightly, docs, evals.

## 5) Ключевые продуктовые возможности (по коду и документации)

- Генерация/изменение кода естественным языком.
- Агентное выполнение задач.
- Интеграции терминала и браузерных действий.
- MCP-экосистема.
- Многорежимная работа (architect/coder/debugger и т.п.).
- Отдельный CLI-режим, включая non-interactive/autonomous сценарии.

## 6) Точки, важные для переноса в UE5

Чтобы сделать аналогичный инструмент как **UE5 plugin**, архитектуру нужно разбить на переносимые слои:

1. **Agent Core (переносимый слой)**

    - Оркестрация сессий, промптинг, tool-calling, state machine задач, контекст.
    - Лучше вынести в отдельный сервис/библиотеку, не завязанную на VS Code API.

2. **Provider Layer (LLM/Cloud/MCP)**

    - Адаптеры к моделям и облаку сделать платформенно-нейтральными.
    - Упростит переиспользование между VS Code/CLI/UE5.

3. **IDE Adapter Layer**

    - Текущая реализация опирается на VS Code (команды, webview, workspace API).
    - В UE5 это нужно заменить на:
        - Editor module + Slate/UMG UI,
        - интеграцию с Content Browser/Asset Registry,
        - работу с C++/Blueprint ассетами,
        - запуск и контроль внешних процессов под UE.

4. **Tooling Layer для UE5**
    - Аналоги инструментов чтения/записи/поиска файлов,
    - “безопасные команды” через sandbox-политику,
    - инструменты анализа C++/Blueprint graph,
    - генерация/патчинг кода в Source/Plugins.

## 7) Риски и сложность при переносе

- Сильная зависимость UX от VS Code webview/command model.
- UE5 UI/UX сильно отличается (Slate/Editor tab system).
- Нужна отдельная стратегия для Blueprint (не только текстовый код).
- Асинхронность и потоковая модель ответов в UE Editor нужно проектировать отдельно.
- Политики безопасности выполнения команд в контексте движка должны быть консервативнее.

## 8) Предлагаемый путь создания UE5-плагина аналога

### Фаза A — MVP (2–4 недели)

- Чат-панель в UE5 Editor (Dockable tab).
- 2–3 инструмента: чтение проекта, поиск по файлам, создание/изменение C++ файлов.
- Провайдер 1–2 LLM + базовая конфигурация ключей.
- Логи/история задач.

### Фаза B — Практическая полезность (4–8 недель)

- Контекст ассетов (uasset metadata), классов/модулей.
- Инструмент “Fix build errors” (парс логов UBT/Compile).
- Инструмент “Generate boilerplate” (Actor, Component, Subsystem).
- Политика подтверждений на опасные действия.

### Фаза C — Продвинутая агентность

- Планирование multi-step задач и авто-проверки.
- Интеграция с git-операциями.
- Опциональный удалённый backend для тяжёлых операций (индексация/эмбеддинги).
- Частичная поддержка Blueprint-рефакторинга через Editor API.

## 9) Вывод

Да, **помочь создать аналогичный инструмент в виде UE5-плагина я могу**.

Оптимальный формат: спроектировать совместимую “core + adapter” архитектуру и затем итеративно собрать UE5 plugin, начиная с рабочего MVP. Это реалистичная задача, но это **не прямой copy-paste** из VS Code-расширения: нужен системный адаптационный слой под UE Editor.
